# Security Model

KeyValet installs a sudoers rule and runs code as root, so it is important to be precise about what it protects against and what it does not.

## Reporting a vulnerability

Please **do not** open a public issue. Use GitHub's private vulnerability reporting ("Security" tab → "Report a vulnerability") on this repository. Include steps to reproduce and the affected version/commit. We aim to acknowledge reports within a few days.

## Assets

- Static secrets (API keys, passwords, tokens) and their extra secret fields.
- Long-term protocol secrets: OAuth client secrets and refresh tokens, Google service-account private keys, GitHub App private keys, JWT signing keys, TOTP seeds, AWS secret access keys.
- The vault master key, and the integrity of the audit log and settings.

## Trust boundaries

| Component | Runs as | Trusted? |
|---|---|---|
| AI agent / MCP client | your user | **Semi-trusted.** May be prompt-injected. May speak MCP to the KeyValet server *and* may run arbitrary commands as your user (including talking to the helper directly). |
| KeyValet MCP server (`rust/crates/kv-mcp`) | your user | Convenience layer. **Security checks never rely on it alone.** |
| Vault daemon (`rust/crates/kv-helper --daemon`, label `dev.keyvalet.helper`) | root | Trusted. A `launchd` daemon serving one session per connection on `/var/run/keyvalet/helper.sock` (peer uid must be the installing user's; uid 0 gets only a `control` status query). Holds no vault key while idle: every connection still unlocks with fresh device-owner authentication and drops its key when it closes. |
| Per-user agent (`kv-touchid --agent`, label `dev.keyvalet.agent`) | your user | Trusted after verification. `launchd` cannot do Secure Enclave / LocalAuthentication work, so all prompts and hardware derivations go through this LaunchAgent in your GUI session. The daemon accepts it only after checking its peer uid AND its code signature (`identifier "dev.keyvalet.touchid"`, Apple-anchored, team `PWCRJPY7YC`, exact installed path), so a same-user process cannot impersonate it and approve prompts for you. |
| Root helper (`rust/crates/kv-helper`, stdio mode) | root | Trusted. Enforces every security decision. Kept as the fallback for machines without the team signature: `sudo -n` spawns it per session exactly as before (the sudoers rule stays this version). |
| Touch ID program (`rust/crates/kv-touchid`) | your user | Trusted binary: root-owned, hardened-runtime signed. Authorization returns an exit code; hardware operations return the derived AES key through an anonymous pipe. Every dropped child (this program and the `osascript` dialogs) runs with exactly the invoking user's uid/gid and a single group; uid 0 or gid 0 drop targets are refused, and `kv-touchid` itself exits if launched with any root or wheel identity. |
| macOS (sudo, LocalAuthentication, osascript, launchd, Security.framework) | — | Trusted. |

## What KeyValet guarantees

Assuming macOS and the installed files are not compromised:

1. **No secret without the device owner.** The vault (`/var/db/keyvalet`, root, `0700`, AES-256-GCM) is only readable by root. When the launchd daemon is installed, the MCP server connects to `/var/run/keyvalet/helper.sock` directly (the daemon accepts only the installing user's peer uid, or a root `control` query); otherwise the only passwordless sudo rule allows exactly `/usr/local/lib/keyvalet/bin/kv-helper`. Before serving any request, either path requires device-owner authentication (Touch ID, or the login password in the system dialog) with the vault authorization scope shown.
2. **You set the cadence, and only you can loosen it.** Grant modes: `per_use`, `per_credential` (default; approving one credential does not unlock others), `per_session`, `remember` (N hours across sessions). The mode lives in root-only settings; loosening requires device-owner authentication (Touch ID) in the root helper, so an agent cannot loosen it by itself — not even via the `/keyvalet:mode` slash command it may be asked to run. Clients can only tighten it (`KEYVALET_GRANT_MODE`).
3. **Long-term protocol secrets never leave the root helper.** Agents receive only derived, short-lived material (access tokens, installation tokens, signed JWTs, TOTP codes, STS credentials) or proxied responses.
4. **Proxy-only credentials are never revealed** through `get`, `accessToken`, error messages or (best effort, see below) proxied responses.
5. **Secrets go only where you allowed.** Proxied requests: HTTPS, port 443, exact/wildcard domain allowlist (no IPs, no localhost), no redirects. OAuth/service-account/GitHub/AWS endpoints must be HTTPS; changing an OAuth credential's endpoints or client requires re-entering the client secret.
6. **The local gateway is token-gated and loopback-only.** `credential_gateway` listens on `127.0.0.1` inside the root helper. Each route needs a 32-byte random token bound to one credential and the current session; requests must target `127.0.0.1`/`localhost` (DNS-rebinding protection); client-supplied auth headers are dropped; the host allowlist, no-redirect rule and (streaming) redaction apply exactly as for proxy calls; every request is audited without the token or query string. Reusable gateways are rejected in `per_use` mode; changing the effective grant mode revokes existing gateway tokens, including when the mode is tightened from the terminal or another session, and revocation also cuts off requests already in flight (a streaming response is aborted, not ended normally).
7. **Exposure can only grow with your consent, enforced in the helper.** Adding allowed hosts, changing the injection rule, disabling proxy-only, removing the proxy config, overwriting or deleting a credential, and switching to `all` grant mode each require a confirmation dialog shown by the root helper (as your user via `osascript`). Bypassing the MCP server does not bypass these.
8. **Secrets typed by you don't pass through the agent.** Values are entered in native dialogs (whose text contains only validated identifiers and hosts) or imported from files after you confirm the path.
9. **Every use is recorded.** Unlocks, grants, reads, token fetches, proxied calls (method, host, path — not the query) and configuration changes are appended to a root-only audit log with session ID, purpose and result. Secret values are never logged.
10. **The helper builds the authorization prompt and binding itself.** Clients submit the complete operation and parameters; client-provided hints and digests are not trusted. Session prompts (`per_credential`, `per_session`, `remember`) show the credential plus what the grant exposes, derived from the stored record rather than from the operation the client names: a static credential that is not `proxy_only` always carries the plaintext disclosure warning, because the grant allows reading it. Per-use prompts show the actual operation and every parameter it is bound to: method, host, path, query, agent headers and a body line for proxied calls (for known APIs — OpenAI, Anthropic, GitHub, Stripe, Slack, AWS — the body line is built by the helper from a fixed whitelist of business fields such as `model`, `amount` or `channel`, never from arbitrary body content; other hosts get a shortened raw preview); scopes, repositories and permissions for tokens; the lifetime for AWS credentials. Operations a credential kind cannot perform, unsupported methods and URLs outside the allowlist are refused before any prompt. The full purpose and source context are recorded in the audit log. In `per_use` mode, one approval is bound to the operation type, complete parameters and root-owned credential/test configuration. Replacing an HTTP operation with a raw read, changing the request or stored configuration, or replaying an approval fails closed. Other modes authorize the credential for their documented scope, rather than a particular HTTP request.
11. **Session-bound.** In daemon mode a session is exactly one client connection: the socket closing ends the grant and drops that session's vault key. In stdio fallback mode the helper lives only as long as the MCP server's stdio pipe. Either way, when the agent session ends, the grant ends.
12. **Secure Enclave is required on macOS.** Installation initializes a hardware vault or explicitly collects a recovery passphrase and migrates the old vault. Migration rotates the file master key, atomically commits new ciphertext and hardware metadata, and removes `master.key` after success. New vaults never generate file keys. File-key vaults cannot serve normal helper or CLI operations; legacy parsing is retained only for migration and recovery of historical data. The device-bound hardware private key has a `userPresence` ACL and cannot be exported in plaintext through the API. Its opaque key representation is stored only in root-only vault files (`vault.enc`), passes only through the hardened-runtime `kv-touchid` over a private pipe, and is never returned to clients or printed by `keyvalet protection`. Vaults set up or rotated by this version also mix a root-only device binding secret (`device-binding-<id>.key`, excluded from Time Machine) into the vault key, so a copy of `vault.enc` alone plus one approved prompt does not decrypt it; `keyvalet protection` reports `device_binding` and `binding_excluded_from_backups`, and `keyvalet rotate-recovery` adds it to older vaults. Each key change — setup, migration, recovery, rotation — creates a fresh `device-binding-<id>.key` and removes the older ones after commit, so earlier copies of `vault.enc` on this Mac then need the recovery passphrase. Each new helper session uses a fresh authentication context, including during `remember` windows. Hardware operations run as the logged-in user inside that user's GUI security session (inherited through `sudo`), the same context as a command typed in Terminal; Apple does not support Secure Enclave use from `launchd` daemons, and headless / SSH sessions may fail. Hardware failures, cancellation, unavailable devices or corrupt metadata never enable a software fallback. If Secure Enclave becomes unusable, `keyvalet recovery-read` gives explicit read-only access with the recovery passphrase (writes are rejected) and `keyvalet recover-vault` rebinds on a working Mac; `keyvalet recovery-check` verifies the passphrase without hardware or changes. `keyvalet rotate-recovery` replaces the hardware key, vault key and recovery passphrase together after a hardware unlock, which revokes the old passphrase for the current vault. Protection status is exposed by `keyvalet protection` and session status.

Raw tool results are never copied into a plaintext matching cache. Hooks detect recognizable key/password formats without retaining returned secrets. Explicit secret exports and gateway environment files are created with `0600` relative to verified user-owned `0700` directory descriptors, without following symlinks. Locking (even when forgetting `remember` fails), expiry, helper disconnect and MCP shutdown delete session files and reject late writes. Each file is tagged with its creator's PID and process start time, so startup removes files left by crashed sessions even after PID reuse, along with legacy `.redact` files and exports named by older versions. Raw values already returned to a caller cannot be revoked or erased from that caller's memory or records. Provider error diagnostics are omitted; only status, fixed OAuth error codes and well-formed AWS error codes are returned, and helper errors are sanitized before response and audit. Purpose text has control, bidi-override and zero-width characters removed before it reaches dialogs or the audit log.

## What KeyValet does NOT protect against

- **Misuse of a grant you approved.** Once a session holds a grant, a malicious or prompt-injected agent can use that credential (e.g. make proxied calls to allowed hosts, or read the value of a non-proxy-only static credential). Use `proxy_only`, narrow `allowed_hosts`, scoped tokens and per-use mode to limit this. Read the credential and scope in the Touch ID prompt, along with the operation shown for per-use approvals and non-proxy access.
- **Gateway tokens authorize repeated calls until lock, session exit or a grant-mode change.** They are available only outside `per_use` mode; a URL alone does not authorize access. Keep the token private.
- **`remember` mode trades prompts for exposure.** Unlocked sessions can use credentials without further prompts during the window. Every new session still requires hardware authentication. Keep the window short; `/keyvalet:lock` ends it.
- **The stated purpose is unverified.** It's the agent's free-text claim, recorded in the audit log (not shown in prompts) but never checked against what actually happens afterward. The helper derives the operation/request line independently and binds it in `per_use` mode (see guarantee 10); in `per_credential`/`per_session`/`remember` mode it isn't — a compromised MCP server could show one request to get the credential authorized, then use the grant for a different one for as long as the grant lasts.
- **Approving a malicious prompt.** Malware running as your user can trigger the same Touch ID prompt (the source directory in the audit log is supplied by the client). If you approve it, it gets the grant.
- **Upstream reflection beyond redaction.** Responses are redacted for the exact secret and common encodings (URL, form, JSON escapes, base64/base64url, hex, case-insensitive), and binary responses containing a secret are refused — but an allowed host that transforms and echoes a secret in some other encoding could still leak it. Only allow hosts you trust.
- **Compromise of root or macOS**, physical attacks, or a compromised build: on Apple Silicon the installer downloads the prebuilt arm64 archive attached to the GitHub release (built by GitHub Actions from the tagged commit) and verifies it against the `SHA256SUMS` file published in the same release — for releases built by the release workflow, every binary in that archive is also codesigned with the Simvito Limited Developer ID (team `PWCRJPY7YC`, hardened runtime, timestamped; v0.2.0 and later are also notarized by Apple, and the release job fails if Gatekeeper rejects the binaries), and the installer verifies that signature before enabling daemon mode — while `SHA256SUMS` remains the download integrity check, not authenticity by itself; Intel Macs and versions without release assets still download the repository source over HTTPS and build it locally with `cargo build --release --locked` (exact dependency versions from the committed `Cargo.lock`), with no signature or checksum on the downloaded source. Audit the release or the source yourself if that matters to you.
- **Compromised root, at any time — not only during an unlock.** Secure Enclave protects the private key, but ECDH + HKDF derives a fixed AES key that is delivered to the ordinary root helper. The CryptoKit key representation in `vault.enc` is bound to this Mac's Secure Enclave, not to KeyValet's code signature: Apple DTS has confirmed that other — even unsigned — processes on the same device can load such a representation. Its secrecy rests on root-only file permissions, and the Secure Enclave still enforces `userPresence` on every use. Compromised root can therefore start a derivation itself whenever it likes, with any prompt text (including through KeyValet's own `kv-touchid`); one approval yields the AES key. Root or kernel compromise can also capture the key or plaintext from the helper during a legitimate unlock. A captured AES key decrypts current and earlier vault snapshots offline until rotation. Zeroizing buffers, best-effort `mlock`, hardened signing and disabled core dumps reduce exposure without providing enclave execution of the vault or proxy. For vaults without device binding (created before it existed and not yet rotated), the same applies to any copy of `vault.enc` that a non-root process can read: on the same Mac, that copy plus one approved prompt decrypts it. With device binding, such a copy also needs the current `device-binding-<id>.key`, which only root can read; root itself can still read both. Session prompts show fixed scope text that other programs can imitate, so treat a system authentication prompt you did not just cause as a warning sign, and check `keyvalet audit`.
- **Recovery passphrase compromise.** The recovery wrapper is another decryption path: encrypted `vault.enc` plus its passphrase suffice without the original device or authentication — offline, or through `keyvalet recovery-read` for anyone who can also run `sudo`. Argon2id slows offline guesses; it cannot make weak passphrases safe. If the passphrase may be exposed, run `keyvalet rotate-recovery`: the current vault then needs the new passphrase, but copies made before the rotation still open with the old one. Device password authentication and OS recovery policies are also part of the platform trust boundary.
- **Historical copies and rollback.** Old file keys plus old vault copies remain decryptable. APFS snapshots, backups and SSD remnants are not securely erased by migration. Encryption detects tampering, but KeyValet does not maintain a hardware monotonic counter and cannot detect replacement by an older valid snapshot.
- **Secrets after they are handed out.** Values returned by `credential_get` and short-lived tokens are in the agent's context and may be retained by the model provider.
- **Denial of service.** An agent can delete nothing without your confirmation, but it can spam requests (rate-limited prompts, 30 s cooldown after failed authentication).

## Design notes

- The helper verifies at startup that it and every file it loads are root-owned, not group/other-writable and not symlinked; otherwise it refuses to run.
- Concurrent changes are guarded: credential records carry a random generation ID so that a refresh that completes after the record was replaced cannot write tokens into the new (possibly attacker-controlled) configuration; proxy-config changes re-check the configuration after the confirmation dialog.
- Root-helper hardening: bounded line size, bounded in-flight requests, bounded response sizes (streamed with limits), no automatic decompression.
- The legacy `credential-mcp` vault format (pre-rename) is still readable and is upgraded on the next write.
- Hardware mode uses CryptoKit's opaque encrypted `SecureEnclave.P256.KeyAgreement.PrivateKey.dataRepresentation`, not an exportable private key or persistent Keychain item. A small Swift C ABI bridge is needed for this documented Swift API; process trust, privilege dropping, vault encryption and policy remain Rust. The ECDH peer private half is generated temporarily and discarded; its public half is stored with the opaque hardware key. HKDF-SHA256 uses `keyvalet/master-key/v1` as its domain separator.
- Hardware metadata and the recovery wrapper are bound into AES-GCM additional authenticated data. Migration verifies fresh-process derivation before committing; recovery rotates to a freshly verified device key. No master key or passphrase is passed in argv or environment, written as plaintext to disk, or included in logs. `argon2` is the added cryptographic dependency for password recovery (64 MiB, three iterations, one lane; random 16-byte salt and AES-GCM 12-byte nonce).
- Before explicit migration or recovery the CLI requires all helper sessions to close. New code rejects reads/writes after a key change. Ciphertext and its key metadata live in one atomically replaced file so there is no two-file commit gap. No `vault.migration-backup.enc` is written anymore (it was byte-identical to the new `vault.enc`); a leftover from an older version is removed by `rotate-recovery`, `recover-vault` or `finish-enclave-migration`. A crash before old-key removal is recoverable through the cleanup command; that old key is never a fallback.
- Device binding: vault key = HKDF-SHA256(ikm = the Secure Enclave-derived key, salt = the 32-byte root-only `device-binding-<id>.key`, info = `keyvalet/master-key/device-binding/v1`). Its SHA-256 digest is stored in the authenticated key metadata, so a missing or replaced file is reported before any prompt. Every key change creates a fresh digest-named binding file and removes the previous ones after commit (the legacy `device-binding.key` name is still read); the recovery wrapper wraps the final vault key, so recovery on another Mac does not need it. Deleted binding files can persist in existing APFS local snapshots until they expire. The Time Machine exclusion is applied before the secret is written and `keyvalet protection` reports `binding_excluded_from_backups`; third-party backup tools ignore the exclusion. Older vaults without the binding keep opening until rotated.
- Pending per-use approvals are kept per exact binding (up to 4 per credential, 16 per session), so concurrent calls do not overwrite each other and a mismatched request never consumes another request's approval. An OAuth device-flow poll approval covers repeated polls of that same device code for at most 30 minutes.
- `recovery-check` and `recovery-read` open the recovery wrapper in the root CLI without touching hardware. The vault handle is marked read-only, so writes and legacy-key removal fail until the next hardware unlock; every use is audited with `access: recovery_passphrase_read_only`. This is an explicit emergency path, not a runtime mode: the helper never accepts it.
- A future long-running macOS helper (for example behind a Unix socket) must not perform Secure Enclave operations itself, because Apple does not support Secure Enclave use from `launchd` daemons. Those operations belong in a per-user process in the login session, such as a LaunchAgent the helper verifies.

## Hardening tips

- Keep the default `per_credential` grant mode.
- Store HTTP API keys with templates and set `proxy_only: true` for sensitive ones.
- Prefer OAuth/service accounts/GitHub Apps (short-lived tokens) over long-lived personal tokens.
- Review `keyvalet audit` periodically.
