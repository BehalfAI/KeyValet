## 1. 定位：面向 AI 自动化的凭证授权与调用网关

2026-10-10 确认：**KeyValet 面向 AI 自动化，让各种 Agent 在授权范围内安全使用
凭证，持续完成长任务。** 人管理授权、关键动作审批和撤权，Agent 执行任务，KeyValet
在实际调用时执行权限检查与凭证使用。首批客户是 AI 开发者与使用生产 API 的小团队。

| 主线 | 用户得到什么 | 产品边界 |
| --- | --- | --- |
| 凭证安全 | 通过代理使用长期凭证，限制操作，必要时批准，并可撤销和追溯 | 凭证保管、使用授权、执行保护分别说明；拿不到原始 key 不等于不会滥用已获准的权限 |
| AI 长任务 | 在已批准的范围与期限内持续调用，处理 token 刷新、暂停、恢复和子任务 | 不靠无限期全库授权或自动放宽权限维持运行；持久任务授权和子代理治理仍需实现与验收 |
| 多种 Agent | 不同 Agent 共用凭证、策略与任务授权语义 | 通过 MCP、CLI、HTTP/SDK 等通用入口接入，运行时 hook 单独适配；兼容目标不等于全部已验收 |

AI 自动化是主要产品场景；脚本、SDK、CLI 和 CI 可以复用底层调用机制。保留个人管理
和人工使用 API 的能力，但不把人的日常密码管理作为当前主线。支持状态以
[运行时矩阵](runtimes.md)为准。

也可以把核心架构理解成“凭证调用中枢”：配置各种服务的钥匙，通过同一套入口授权、
调用和审计。它可以运行在本地、自建服务器或官方 SaaS；“中枢”不要求所有秘密集中
保存到官方服务器。面向首批用户的定位建议见 [§8](#8-产品定位与竞品调研)。

用户关心的是：不用把长期 key 到处复制；程序只做获准的操作；关键动作有人批准；能查
谁用了什么；人员离开后能停用访问。加密、TPM、KMS 与 Enclave 为这些要求提供保护。
安全与长任务要一起设计：人在任务开始时批准明确的资源、操作与期限，范围内的调用可
持续进行；扩大范围或执行需要批准的动作时再找人。此流程是目标设计，不能用现有
凭证级会话授权代替并宣称已经具备相同限制。

现有产品已经有 API key、OAuth、终端管理、HTTP 代理与本地 SDK 网关，并不要求每次调用
都由 AI 发起。SDK 网关用会话令牌替代真实上游 key，具体机制见
[使用指南](../site/content/guide.zh-CN.md) 与
[网关实现](../rust/crates/kv-mcp/src/tools/http.rs)。独立于 AI 的网关启动体验、
`keyvalet run` 等便利入口仍需完善，不能把产品规划中的命令当作已发布能力。

### API key 的两类需求

| 用户要做什么 | 产品方向 | 优先级 |
| --- | --- | --- |
| 保存并使用 OpenAI、GitHub、Stripe 等已有服务的 key | 本地库或外部数据源 → 授权 → 代理请求/短期凭证 → 返回结果 | 主线；现有能力的扩展 |
| 给自己的 SaaS 用户签发 API key，并管理权限、限流和额度 | 面向业务 API 的认证与密钥管理服务 | 另一个产品方向，先收集真实需求 |

KeyValet 不能替所有第三方服务创建它们的 API key；要使用对方提供的申请、OAuth 或签发
接口。自己的业务 API key 则还需要业务服务接入验证和权限执行。
已有 [Unkey API 文档](https://www.unkey.com/docs/api-reference/v1/migration/keys)
覆盖创建、验证、权限等功能，说明这个方向也已有专门产品。

### 可扩展的使用场景

| 场景 | 用户得到什么 | 当前与未来的边界 |
| --- | --- | --- |
| 本人用终端调用 API | 少复制 key，统一管理与授权 | 已有 CLI 管理和 HTTP/SDK 机制；完善独立调用入口 |
| Python/Node 脚本或 SDK | 网关替程序持有真实上游凭证 | 已有本地网关；需要逐个 SDK 验证兼容性 |
| AI coding agent | 代理使用凭证、敏感操作审批、泄密拦截 | 当前主要入口；仍需完成各平台与运行时验收 |
| CI/CD | 受限机器身份、短期授权、可审计的部署请求 | 组织身份接入和无人值守执行仍属规划 |
| 自动化任务、后台服务 | 统一凭证轮换与使用控制 | 需要专门的非交互身份和授权策略，不能直接绕过本地用户认证 |
| 团队共享生产 API 权限 | 可以共享使用权，统一收紧策略和撤销成员 | Team 控制面、共享与组织审计仍待实现 |

代理使用、签发短期凭证和导出明文是不同交付方式。CLI 的显式读取/导出会把秘密交给
接收者；短期 token 也会进入调用进程。只有满足相应实现条件的代理路径，才能承诺调用方
拿不到真实的长期上游 key。不能对所有接口统一写成“任何程序都看不到密钥”。

## 2. 五项可组合的选择

| 选择 | 选项示例 | 作用 |
| --- | --- | --- |
| 使用主体 | 个人；组织、成员和机器身份 | 谁拥有凭证、谁可以使用、谁负责付费 |
| 部署方式 | 本地；用户自建 server；官方 SaaS | 控制面与同步服务由谁维护 |
| 凭证数据源 | 本地加密库；1Password、Infisical、Vault/OpenBao、云 Secrets Manager | 凭证从哪里读取，是否在 KeyValet 保存副本 |
| 主密钥保护 | Software；Secure Enclave；TPM2；云 KMS/HSM | 本地密文和数据密钥由什么方式保护 |
| 敏感操作执行位置 | 本机；客户服务器/VPC；云 Enclave | 谁能接触解密后的凭证与请求 |

例如，“个人 + 自建 server + 本地数据源 + TPM + 本机执行”和“团队 + 官方 SaaS +
外部凭证库 + BYO-KMS + 客户云 Enclave”都可以由同一套核心接口组合出来。
设计上分开扩展点，不需要为每种组合独立维护一个产品。

### 软件保护与数据源要分开

外部密钥库属于数据源；Software provider 属于主密钥保护。软件 TPM 模拟器可以用于
测试 TPM 指令，但不能提供等价的硬件隔离。正常兼容模式可直接设计软件 provider，
无需让用户安装模拟 TPM。

建议硬件可用时优先使用硬件；无硬件时允许明确选择软件保护，显示真实保护级别。
已经启用硬件保护的库遇到故障时仍需报错，不能自动降级。软件主密钥的存储、口令派生、
备份和恢复应有自己的格式与说明，不能只改一个状态标签。

**当前状态**：Linux 已有显式软件模式；macOS 仍要求 Secure Enclave；Windows 仍要求
Hello，硬件证明可能为未知。新增 macOS 软件模式是产品与实现变更，列为兼容需求，
待真实用户需求验证后实施；本文没有启用它。

## 3. 免费与收费的边界

建议保留 Free + Team 两档先行，Enterprise 和托管隔离执行后续增加。
**同一个人的本地与自建多机使用免费；组织协作、集中治理和托管服务收费。**
公司员工各自使用本地免费版也免费，收费触发点是使用新增的 Team 能力，而非公司身份。

| 档位/能力 | 建议提供什么 | 收费方式 |
| --- | --- | --- |
| Free 本地 | 本地库、基础策略与审批、CLI/MCP/网关、恢复、本地审计、已支持的硬件或软件保护 | 免费，包括公司员工的个人使用 |
| Free 个人多机 | 本人设备配对、加密同步、自建基础 relay；官方免费 relay 可有合理使用额度 | 自建免费；官方服务按公布的免费额度提供 |
| Team | 组织、成员、共享使用权限、角色、组织策略分发、设备撤销、团队审批、集中审计与机器身份接入 | 按人订阅；官方 SaaS 与自托管商业版可用相同功能分层 |
| Enterprise | SSO/SCIM、更多治理要求、审计系统集成、专用部署与支持 | 年度合同，按实际需求报价 |
| 托管执行附加项 | 设备离线时也能执行；云端隔离执行、部署、升级、监控和容量管理 | 资源或包含配额的套餐另计；客户自付的云账单明确分列 |

基础 KMS/TPM 适配器和软件/硬件保护不按“更安全”单独收费。
客户为公司级策略管理、稳定的托管执行和维护服务付费；使用 AWS/腾讯云 KMS 的资源
账单则由云厂商收取，不能与 KeyValet 订阅混为一谈。

本地审计和用户自己的数据导出属于基础功能；Team 收费点是组织汇总、检索、留存和分发。
安全修复、基础认证和已有本地能力持续向 Free 提供。

## 4. 开源、源码可见与商业服务

遵守现有 [GOVERNANCE.md](../GOVERNANCE.md)：已发布的 Apache-2.0 功能保持原许可，
本地功能免费，基础自托管不依赖官方账号或回连授权。
[Apache-2.0](https://www.apache.org/licenses/LICENSE-2.0) 允许公司使用与分发；不能仅因为
使用者是公司，就把已有开源核心改成必须购买 Team 的功能。

| 部分 | 建议许可/模式 | 商业边界 |
| --- | --- | --- |
| vault、密码操作、关键授权校验、客户端、CLI/MCP、基础 relay、协议 | Apache-2.0 | 免费核心；也可以收费提供托管、集成和支持 |
| 基础数据源与 KMS/TPM 连接器 | Apache-2.0 | 单一连接器不设付费门槛；批量配置、组织治理和运维属于商业服务 |
| Enclave 内的安全执行代码、证明验证和可复现构建 | Apache-2.0 | 用户可验证和自行部署；托管执行与组织调度可以收费 |
| 组织管理、策略分发、团队控制台、组织审计聚合、计费与权益管理 | 新增 `ee/` 模块，源码可见的商业许可 | 提供审阅；生产使用商业功能需获得对应授权，包括自托管 |
| 官方 SaaS、部署与维护服务 | 商业订阅/服务合同 | 源码开放不等于官方运营服务免费 |

源码可见的商业模块应明确标注，不能统称为 Apache 开源。未来 Team 自托管可以用离线
许可证文件或合同授权，不要求免费客户端登录官方服务，也不把付费授权变成密码算法的
旁路。开源核心被其他人改造或托管是许可允许的事实，商业优势需要靠体验、集成与服务建立。

现有开源规划中的 `ee/`“可自用”措辞需要在正式商业条款里明确适用范围，避免与
“企业生产自托管需付费”相冲突。本文只记录许可方向，不修改现有 LICENSE，也不直接
发布商业合同。参考 [Infisical 的开源/商业目录说明](https://github.com/Infisical/infisical)
与其 [企业模块许可](https://github.com/Infisical/infisical/blob/main/backend/src/ee/LICENSE.md)。

## 5. 首批价格与云成本

沿用现有试验锚点：**Team 每人每月 15 美元，年付折算每人每月 12 美元**，
14 天试用、不需要信用卡。先验证这一档，不急着拆个人 Pro、云厂商专用版等多个套餐。
后续手机、多方审批和企业集成的权益归属，在真实使用和维护成本明确后再定。

建议按人计费；机器身份不按每个 agent 或 runner 收席位费，但托管 API、执行并发与资源
设清楚的合理使用或配额规则。公司云账户的 BYO-KMS 账单由客户自己承担。
Enterprise 暂不规定最低五万美元年费，先按部署与支持范围报价。

作为市场参考：截至本次查阅，Bitwarden Secrets Manager Teams 年付折算每用户每月
6 美元；Infisical Pro 定价页年付折算每 identity 每月 20 美元，identity 包括人和机器。
二者都提供免费档，并将部分组织能力放在付费档。
[Bitwarden 定价](https://bitwarden.com/products/secrets-manager/)、
[Infisical 定价](https://infisical.com/pricing)。
这些数字说明可以按团队价值收费，不证明 KeyValet 用户已经愿意付 15 美元。
如果用户只需要存放 key，较便宜的成熟产品会是直接竞争者。

云端隔离执行需先做成本与负载测量，再确定基础费、配额或资源计费。常驻 EC2、预留

## 6. SaaS 的信任边界

SaaS 可以提供组织、身份、策略、审批路由、同步、账单与审计管理，凭证留在用户设备、
客户 VPC 或经过验证的隔离执行环境。数据源、保护 provider 与执行位置分别报告。
基础 relay 只转发密文，不等于所有执行服务器都看不到明文。

普通服务器承担解密和上游 TLS 时，其执行进程会接触凭证，需要信任它的管理员。
只有敏感执行流程留在正确配置的 Enclave 等隔离边界内，并拒绝绕过证明的解密路径，
才能将普通父主机 root 排除出去；KMS 的密钥策略管理权也必须说明。

共享优先设计为共享使用权限，避免为了协作先向所有成员发出长期 key。
撤销成员可以阻止通过在线执行端的新请求；离线令牌在到期前可能仍有使用窗口。
已经导出的秘密、已复制的旧密文与解密密钥、已发出的上游请求不能追溯撤回，必要时还要
轮换上游凭证。不能仅轮换 KeyValet 的数据密钥就承诺原 API key 已经失效。

## 7. 实施与需求验证

按已确认的三条主线安排下一轮验收：先把安全调用用于一套真实 AI 长任务，再在另一种
Agent 上复用同一套规则。记录调用成功率、权限中断原因、批准次数、恢复结果与撤销
生效窗口。新增任务授权属于产品与协议设计工作；当前发布、平台验收与推广的执行顺序
仍以行动计划为准，本文不另定发布日期。

1. **当前本地版**：先完成三平台验收与现有推广计划；补齐独立 CLI/SDK 的使用体验，
   为 AI 长任务保留可复用的调用入口。先用现有能力验收同一任务在不同 Agent 上的调用
   与批准，再补齐任务范围、期限、暂停与恢复机制；人工终端和脚本也复用这些接口。
2. **首个付费闭环**：访谈约 10 个小型开发团队，找到至少 3 家愿意付费试点的团队。
   按他们的共享、撤权与审计需求做 Team；可先单租户部署试点，数据模型从开始包含 Org，
   公开多租户 SaaS 前完成租户隔离与权限验收。
3. **按需求接来源与 KMS**：保留扩展接口，先做付费客户需要的一两种数据源与一家 KMS，
   不以接入厂商数量作为阶段目标。TPM 已有路径继续复用；macOS 软件模式按兼容需求安排。
4. **无人值守与隔离执行**：有客户需要电脑离线运行、并愿意承担资源费后，先实施
   AWS Nitro Enclaves + KMS。执行代码可验证，托管和组织调度收费；其他云按需求扩展。

这些是投入顺序建议；沿用“本地版完成后先推广、按数据决定是否进入 Team”的最新决定，
不承诺新的发布日期。仅凭支持更多后端或算法，不足以进入下一阶段。

## 8. 产品定位与竞品调研

### 8.1 面向用户的定位

确认表述：**KeyValet 是面向 AI 自动化的凭证授权与调用网关，让各种 Agent 安全使用
凭证，持续完成长任务。** 人负责授权、审批和撤权；人工终端、SDK、MCP 和 CI 可以共用
授权与执行机制，具体入口按已实现能力逐项开放。

“凭证调用中枢”说明内部架构；对外先讲清楚目标用户和他们要完成的任务：接入是否方便、
是否能继续使用已有密钥库、审批是否顺手、共享使用之后能否撤权。共享、外部数据源与
CI 接入仍按本文前面的规划与实施边界推进。

目标流程示例：

```text
人定义授权范围与期限
        ↓
Agent / 子任务 → KeyValet 检查权限 → 携带凭证调用上游 API → 返回结果、记录审计
                        ↓
                 需扩大范围或敏感动作时请人批准
```

配置 Cloudflare、Airtable 等服务的凭证后，可以共用通用 HTTP 调用机制；精细到具体
业务操作的权限和审批，还需要对应服务的适配与验收。代理路径、短期凭证和明文导出
继续分别说明，见 [§1](#1-定位面向-ai-自动化的凭证授权与调用网关)。

| [1Password for Claude](https://support.1password.com/1password-claude-security/) | Mac 本地应用配对、用户批准和会话授权；将凭证交给浏览器扩展完成自动填充，向 agent 返回概要和状态 | 本地授权与 AI 凭证使用已有大厂进入；这里比较的是浏览器自动填充能力 |
| [Keypo](https://github.com/keypo-us/keypo-cli) | 本地 Secure Enclave 密钥与加密库、Touch ID、向命令环境变量注入秘密；有公开源码 | 本地硬件保护路线已有相近项目；环境变量注入会把秘密交给执行进程 |

Infisical 两个版本分别比较。不能只把竞争范围理解为传统的凭证保管，也不能把
“不给 AI 真实 key”“本地硬件保护”“有开源版本”“长任务会话”或“子代理授权”单独
当作独有能力。不同产品对代理、凭证交付和浏览器填充的信任边界不同，本文不据此给出
安全强弱排名。

旧规划中的“1Password 管你的登录，KeyValet 管你的 API”不足以描述目前的竞争范围；
后续对比文案应依据具体调用方式、身份与授权流程，使用上表的公开能力作为参考。

### 8.3 KeyValet 值得争取的区别

这些是需要用试点证明的体验优势：

1. **个人上手简单**：安装、添加凭证、接入 CLI 或 AI 后，很快完成第一次真实调用。
   再验证脚本和 SDK 能否复用同一套规则，减少复制长期 key 的操作。
2. **兼容已有凭证库**：后续可接在 1Password、Infisical、Vault 等数据源前面管理调用，
   让用户继续使用已有保管方式；这些外部连接器仍按需求实施。
3. **审批信息有用**：清楚显示哪个程序使用哪份凭证、请求什么操作；按风险安排自动
   放行和人工批准，精细操作由对应服务适配与验收支持。
4. **长任务可以持续又能收权**：验证任务权限与单次执行 token 分离、恢复时重新检查
   授权、子任务受父授权上限约束；用同一任务在不同 Agent 上比较中断与恢复体验。
   这些是候选实施与验收要求，竞品已有相近机制，不能作为独有功能宣传。

当前已有的是本地凭证、认证授权与代理能力，仍需完成各平台验收；团队控制面、外部
密钥库连接器、KMS 与云隔离执行仍属规划，不能计入已发布能力。与竞品比较时，应验证
接入时间、日常使用成本和授权边界，而不是用计划中的功能数量推导已经更强。

| 凭证类型 | 静态 key、Basic、自定义请求头与 OAuth 2.0；OAuth 可连接服务或粘贴 token，支持自动刷新 | 服务文档列出 Bearer、Basic、pass-through、自定义头和占位符替换；本模块自动 OAuth 刷新的完整流程未确认 |
| 授权单位 | 实例角色与 vault 角色；Agent 可获多个 vault 的独立角色；proxy 角色只代理调用和提出配置申请 | 用户、组、机器身份先获得产品成员权限，再获得 bundle 授权；任务会话绑定一个 bundle |
| 请求限制 | 域名、端口、路径 glob；文档明确匹配不看方法、请求头、查询参数或请求体 | 服务可限定 HTTP 方法与路径前缀；路径按完整片段匹配，非业务字段权限 |
| 人工批准 | Agent 提交 proposal，申请新增、更新、删除服务或凭证；人通过浏览器或 CLI 批准 | 管理员配置 bundle 并授予使用权，获授权的用户或机器身份自行创建会话；未查到与开源 proposal 等价的流程说明 |

[Credential stores](https://docs.agent-vault.dev/learn/credential-stores)。
静态/OAuth 生命周期见 [Credentials](https://docs.agent-vault.dev/learn/credentials)，
角色见 [Permissions](https://docs.agent-vault.dev/learn/permissions)。
两种匹配规则与认证方式分别见
[开源 Services](https://docs.agent-vault.dev/learn/services)和
[平台 Services](https://infisical.com/docs/documentation/platform/agent-vault/services)。
平台的组织授权、会话与网络协议分别见
[Access control](https://infisical.com/docs/documentation/platform/agent-vault/access-control)、
[Sessions](https://infisical.com/docs/documentation/platform/agent-vault/sessions)和
[Proxies](https://infisical.com/docs/documentation/platform/agent-vault/proxies)。

**开源版已有“Agent 申请、人提供凭证并批准、Agent 继续”的闭环。** proposal 中包含
服务配置、凭证槽位和申请说明；人可以输入 API key 或完成 OAuth 连接。批准后配置合并
进 vault，Agent 查询申请状态后重试。它批准的是配置变更，同一 vault 内有代理权限的
其他 Agent 也可能使用新增服务；不能把它解释成只允许申请者执行一次具体业务操作。
[Proposals](https://docs.agent-vault.dev/learn/proposals)。

**平台版撤销有传播与网络边界。** 默认每 60 秒检查会话，轮询间隔可配置为 10～300 秒。
撤销后停止提供真实凭证，丢失 bundle 授权的请求可能仍以无凭证方式转发，是否到达上游
由 traffic policy 决定。默认 Any host 会放行未配置主机的无凭证流量，需选
Access bundle hosts only 才拒绝其余主机。控制面不可达时，文档允许代理继续使用最近
会话数据五个轮询间隔，之后返回 502。正常联网的传播时间不能写成所有故障下的绝对
撤销保证。[代理策略与轮询](https://infisical.com/docs/documentation/platform/agent-vault/proxies)、
[授权变更](https://infisical.com/docs/documentation/platform/agent-vault/sessions)。

**平台日志不是业务数据的完整副本。** session logs 记录时间、代理、方法、域名、
路径、状态、匹配服务与放行结果，不记录请求体、响应体、头或 query。日志上传失败时
请求仍可能已执行，因此不能宣传为强制审计成功后才执行。此功能在 Cloud 属于
Enterprise；自行部署也需对应企业许可及用户 S3。普通 Infisical Pro 的 identity
价格不能当作 Agent Vault 完整审计套餐的报价。
[Session logs](https://infisical.com/docs/documentation/platform/agent-vault/session-logs)。

**凭证隔离取决于角色与部署。** 开源版的 vault admin/member 可显式读取凭证，
proxy 角色 Agent 不能读值。其内置存储使用 AES-256-GCM；有主口令时用 Argon2id
派生包裹密钥，无主口令模式会把 DEK 明文存入数据库，依赖部署的文件与平台权限。
解密后的凭证进入普通代理内存；本次未找到此 Agent 产品使用设备 TPM/Secure Enclave
或独立云 Enclave 的执行说明。
[Security](https://docs.agent-vault.dev/learn/security)。

代理包装也不构成沙箱：开源版文档明确说本地子进程可绕过代理，继续访问本机已有凭证
和网络。两版均建议隔离代理主机与 Agent；代理授权保护的是经它使用的凭证，其他
文件中的秘密需另外清理和隔离。[本地包装边界](https://docs.agent-vault.dev/agents/overview)、
[平台部署建议](https://infisical.com/docs/documentation/platform/agent-vault/proxies)。

### 8.5 Keychains 授权与子代理机制

核对日期：2026-10-10。定位是 AI 凭证委托代理；以下功能按官方文档记录，公开代码
核对限于 Satellite Proxy，未实测其托管权限服务、撤销延迟或完整服务兼容性。

| 能力 | 具体机制 | 对长任务的意义 |
| --- | --- | --- |
| API 代理 | CLI 包装 curl，或通过 SDK；请求使用凭证占位符，服务端注入 OAuth token、API key 或 Basic 认证 | Agent 可以调用已有 API，不需要持有其长期凭证 |
| 机器身份 | 本地生成 Ed25519 密钥，通过签名挑战验证；文档还列滚动状态和机器指纹 | 用于验证运行方身份；不能据此认定私钥受 TPM 或 Secure Enclave 不可导出保护 |
| 任务授权 | 一台机器可以创建多个 Permission Request；每份可对应一个任务，保存独立权限状态 | 不必把所有任务合成同一个长期授权 |
| scoped 模式 | 预先声明 scopes，人可批准一个子集；批准后集合不能再扩大，越界返回硬性 403 | 适合权限事先已知的自动化 |
| wildcard 模式 | 初始零权限，每遇到新的 scope 才生成批准链接；已经批准的范围可持续使用 | 允许探索式任务申请新增范围，wildcard 不等于默认全权 |
| 执行 token | 短期 JWT 通常为 5～15 分钟，文档称每次代理调用查询服务端权限状态 | token 到期与任务授权到期分别处理，合法身份可在授权有效时继续获取执行 token |
| OAuth 刷新 | 服务端保存并刷新 access token，Agent 不管理 refresh token | 上游 token 过期不必重新向 Agent 暴露长期秘密 |
| 子代理 | 创建有独立身份和 TTL 的 delegate；固定子集或从零开始逐步申请 | 可以把部分权限交给 worker、VM 或 CI，并控制其有效期 |
| 权限上限 | 子代理只能使用或申请父授权已批准的 scopes，超过父范围直接拒绝，不给批准链接 | 子任务不能自己向用户扩权，绕开父任务边界 |
| 连带撤销 | 官方说明父授权撤销会使所有 delegates 失效；请求检查授权链 | 收回父任务访问时，不需要逐个遗留 worker 清理；延迟仍需实测 |
| 审计与管理 | 文档列机器、任务授权、provider、方法、接口、状态等记录，控制台可查看，API 可查询/导出 | 可以按运行方和任务追溯，不能据此宣称具备业务数据或完整意图审计 |

调用与任务身份见 [Quickstart](https://keychains.dev/docs)、
[How it works](https://keychains.dev/how-it-works)；两种授权见
[Permissions](https://keychains.dev/docs/permissions)；子任务上限、TTL 与撤销见
[Delegation](https://keychains.dev/docs/delegation)；执行 token、OAuth 刷新与审计模型见
[Architecture](https://keychains.dev/docs/architecture)；管理边界见
[API reference](https://keychains.dev/docs/api)。

**子代理审批有两层检查。** 先检查所需 scope 是否在父授权集合中，不在则返回
scope_refused；在父集合内但子代理尚未获准，wildcard 子代理才可请求用户批准。
scoped 子代理固定为已指定子集，不动态扩大。委托私钥仍属于秘密，被盗后攻击者可能在
委托权限和有效期内签发执行 token，需撤销 delegate。
[委托模式](https://keychains.dev/docs/delegation)、
[密钥与 token 被盗后的边界](https://keychains.dev/docs/security)。

**短 token 不是长任务的全部生命周期。** 其公开模型分别保存机器身份、任务权限、
delegate 身份和短期执行 token。任务权限被撤销或版本变化后，旧 token 可被拒绝，
无需等 JWT 自然到期；“立即生效”是官方描述，不是本次测得的指标。
盗用机器私钥的滚动状态检测也有条件：官方威胁模型说明，真实机器空闲时可能要等下一次
合法认证才发现异常，不能写成任何私钥盗用都在第一次请求前被阻止。
[架构](https://keychains.dev/docs/architecture)、
[Threat model](https://keychains.dev/docs/threat-model)。

**自托管 Satellite Proxy 不等于完整自托管。** 默认由官方代理执行 API 请求；
Satellite 可以让请求正文和响应经过用户自己的主机，但代理仍向官方服务提交目标 URL、
方法和占位符，获取真实凭证后在自己的进程里注入。官方仍承担凭证解析和权限判断，
此路径不能称为完整离线或凭证从未经过官方服务。
[部署说明](https://keychains.dev/docs/satellite-proxy)、
[resolveAndFetch 源码](https://github.com/interagentic/keychains.dev_proxy/blob/main/lib/keychains-api.ts)。

公开代理代码还列有 HTTP 流式响应处理，以及非流式请求遇到上游 401 后申请刷新并重试
一次的路径；这不等于任意协议、任意长连接或持久任务重试都已支持。
[请求入口](https://github.com/interagentic/keychains.dev_proxy/blob/main/app/%5B...path%5D/route.ts)、
[HTTP 转发](https://github.com/interagentic/keychains.dev_proxy/blob/main/lib/forward.ts)。

**scope 批准不等于动作意图检查。** 官方威胁模型举例：获准 github::repo 后，Agent
仍可能被诱导执行破坏性仓库操作。它承认无法阻止已批准范围内的错误调用，也不防 API
响应数据被 Agent 泄露。目的地绑定保护凭证的投递范围，但不能据此宣传用户数据不会
进入 Agent。[官方限制](https://keychains.dev/docs/threat-model)。

### 8.6 具体业务操作与安全边界

用于比较的候选任务：让 Agent 连续运行六小时，只调整某个 Cloudflare DNS 记录的
内容，不能改名称或类型，不能删除；扩大权限或敏感动作需另行批准。这是验收场景，
不是任何产品已具备的功能声明。

Cloudflare 更新记录使用 PATCH 接口，记录 ID 在路径中，名称、类型、内容等由请求体
指定。域名、方法、路径与请求体字段是不同的权限维度。
[Cloudflare 更新记录 API](https://developers.cloudflare.com/api/typescript/resources/dns/subresources/records/methods/edit/)。

| 要求 | 从公开机制能确认什么 | 仍需证明什么 |
| --- | --- | --- |
| 只到指定服务、指定记录 | Infisical 平台版有方法与路径前缀限制，可围绕记录路径配置；Keychains 有 provider/scope 检查 | 规则匹配、端口、路径编码和其他替代接口不会突破授权 |
| 只改内容，不能改名称或类型 | 更新接口把不同字段放在同一请求体；方法和路径允许本身不构成字段限制 | 本次未查到两者对此业务字段的现成检查说明；需服务适配、字段策略与实际验证 |
| 删除需单独批准一次 | Infisical 的配置 proposal、Keychains 的 scope 批准都已有流程 | 与具体删除请求绑定、不能换参数执行、不能重放，不可由普通范围批准推导 |
| 持续六小时、能刷新 token | 两者已有会话、长期身份或 token 刷新机制 | 暂停/恢复、身份轮换、授权版本变化时如何继续，不能默默延长期限或扩权 |
| 父任务撤销后 worker 也停止 | Keychains 文档明确连带撤销；Infisical 已有会话与 grant 撤销 | 在线传播、控制面故障、worker 重启和已发出请求的实际边界 |
| 不把真实 key 交给 Agent | 相应角色与代理路径下均有凭证注入机制 | 代理主机、日志、响应、导出和旁路的信任边界；代理自己的权限 token 仍可能被盗用 |

凭证安全至少分为保管、使用授权、执行和返回数据四个边界。只有主密钥不可导出，
不能证明代理进程看不到秘密；只有 scope 检查，也不能证明 AI 执行了用户想要的操作。
本次在两套 Agent 产品文档中未找到明确的设备 TPM/Secure Enclave 使用流程或独立云
Enclave 敏感执行链，属于未确认项，不能写成已证实没有此能力或 KeyValet 已全面更安全。

### 8.7 KeyValet 的差异验收

竞争判断修订：**凭证代理、人工批准、限时会话、长任务身份、OAuth 刷新和子代理授权
已有直接竞争。** 安全、AI 长任务、多 Agent 是产品主线，商业差异需要通过具体任务
验收与持续使用证明，不能靠重述这些通用能力。

| 主线 | 下一轮要验收的内容 | KeyValet 当前与规划的区别 |
| --- | --- | --- |
| 安全 | 代理方的真实身份、凭证版本、目标资源、操作和参数进入授权校验；高风险批准不能被换请求或重放 | 本地 per_use 已有完整操作摘要校验，普通 HTTP 批准一次消费；可复用 SDK 网关在 per_use 下被拒绝。第三方字段策略与自动风险分级仍待实现 |
| AI 长任务 | 任务授权与短 token 分开；资源、操作、期限明确；范围内持续运行；暂停或重启后重新检查；到期、撤销、OAuth 失效有可处理的结果 | 当前有本地会话授权与 OAuth/代理机制；持久任务授权、父子权限链、跨设备恢复和组织治理仍属规划 |
| 多 Agent | 同一凭证与任务规则，通过至少两种 Agent 完成相同任务；调用、审批、错误、恢复语义一致；hook 故障不被算成核心权限检查 | 已有 MCP、本地 HTTP/SDK 与部分运行时适配；真实运行时与平台完成度按矩阵逐项记录 |

当前一次操作绑定见 [授权实现](../rust/crates/kv-core/src/dispatch.rs)；
默认凭证级授权和 per_use 的保证分别描述。已有请求绑定不等于已经理解 Cloudflare
字段的业务语义，也不证明竞品没有等价机制。平台与运行时状态见
[runtimes.md](runtimes.md)，任务验收和阶段顺序见 [§7](#7-实施与需求验证)。

比较时使用同一套任务、上游权限与部署信任条件，记录接入耗时、连续调用成功率、
批准次数、权限中断、恢复方式、撤销窗口、子任务残留访问和维护成本。来源中未确认的
细节应保留为待实测项，不以产品页上的“任意 API”“所有 Agent”代替兼容验收。

本次证据来自公开文档和 Satellite 代码，没有注册竞品账号、使用真实凭证或测试破坏性
调用。Keychains 安全白皮书版本为 1.1（2026-02），对 JWT 是否包含 scopes 的描述与
架构页存在差异；Satellite README 对目标接口可见性的表述也不能覆盖实际发送目标
URL 的代码行为。安全保证以明确的实现、部署条件和后续验证为依据，不将营销描述当作
审计结论。[安全白皮书](https://keychains.dev/api/whitepaper)、
[架构页](https://keychains.dev/docs/architecture)、
[Satellite 仓库](https://github.com/interagentic/keychains.dev_proxy)。

## 9. 商业机会与付费验证

### 9.1 需求信号与证据边界

[Stack Overflow 2026 开发者调查](https://survey.stackoverflow.co/2026/ai) 将编程助手与
agent 列为主要 AI 使用场景，也显示用户更愿意在能够验证结果时信任 AI。
这支持围绕开发工作流设计产品，但不能直接推导需要生产 API 权限的用户规模。

[GitGuardian 2026 凭证泄露报告摘要](https://blog.gitguardian.com/the-state-of-secrets-sprawl-2026/)
记录其在公开 GitHub 的 MCP 相关配置中发现 24,008 份独立秘密，其中 2,117 份被确认
为有效凭证；有效性指报告检测时的结果。这说明配置中的凭证暴露有实际样本，不代表
KeyValet 能防住所有泄露，也不能把这些数量当作潜在付费客户数。

已有相近产品和泄露样本支持问题存在；尚未验证的是用户是否需要这套调用方式、接入
成本是否可以接受、以及谁愿意持续付费。本文不估算总市场规模、转化率或创业成功概率。

### 9.2 商业机会判断

判断：**值得用付费试点验证成为一门有收入的开发者生意；能否做成大平台，仍缺客户
和付费数据。** 价值主要来自共享使用、受限调用、人工审批、机器身份、撤权与可追溯性。
AI 自动化与长任务是主要使用场景；人管理授权，脚本和 CI 可以复用接口扩大使用频率。

| 方向 | 本次判断与优先级 | 需要验证什么 |
| --- | --- | --- |
| 个人保存和使用 API key | 免费获客入口，个人付费需求待验证 | 是否反复使用、是否比复制 key 或已有工具更省事 |
| 小团队共享生产 API 的使用权 | 最值得优先做付费验证 | 谁负责权限、共享与审批是否解决实际任务、撤权和审计是否值得续费 |
| 大企业统一凭证平台 | 订单可能更大，但产品完整性、采购信任与销售要求也更高 | 能否满足现有系统集成、身份治理、可靠性和支持要求 |

首批付费任务可以围绕：**团队让不同 Agent 持续执行生产 API 任务，人能明确授予
权限、批准关键动作并随时撤销。** 人工调用与脚本使用保留为共用入口。这与 Free 个人
使用、Team 协作治理的分层一致，不以公司身份本身作为收费条件。

通用加密 API、凭证存储与代理已有云服务和开源实现；本地审批与跨入口治理需要证明
解决了实际操作问题。商业竞争优势应来自可靠集成、顺手的工作流和用户信任，接入云厂商
数量和算法数量不能代替付费证据。

### 9.3 收入规模示意

沿用 [§5 的试验价格](#5-首批价格与云成本)，假设全部按月付价购买：

```text
100 家团队 × 每家 10 个付费席位 × 每月 15 美元
= 每月 15,000 美元
= 年化订阅收入 180,000 美元
```

这只是收入规模计算，不是已实现收入或客户预测。假设未计折扣、流失、退款，也未扣除
服务、支付、支持和获客成本；年付 12 美元锚点与托管执行附加费未纳入这个示例。
无需先证明能成为大平台，仍可以通过较小规模的团队订阅验证生意。

### 9.4 下一轮付费验证

沿用 [§7](#7-实施与需求验证) 的访谈与本地推广顺序，争取 **至少 3 家真实付费、连续
使用一个月的团队**。这是验证目标，不是新的发布日期或客户数量预测。

- 优先围绕 Cloudflare、Airtable、GitHub 等候选服务完成一套真实任务，再按客户需求
  扩展；通用 HTTP 支持与细权限适配分别验收。
- 观察是否每周重复使用、是否多人确实需要共享生产 API 的使用权、审批是否影响效率。
- 记录负责人是否愿意支付并续费，以及选择 KeyValet、保留原工具或自行搭建的原因。
- 比较接入成本与日常维护成本，确认新增连接器或云执行能解决已有客户的具体问题。
- 对照 Infisical 的两个版本与 Keychains 运行相同长任务；按 §8.7 记录真实授权、
  中断和恢复差异，不能把它们已支持的代理、会话或委托机制当作未被满足的需求。

在持续使用与付费证据出现后，再增加数据源、云适配和隔离执行。仅有关注、点赞或
“技术很酷”的反馈，不足以扩大投入；真实试点数据用于下一次产品取舍。
